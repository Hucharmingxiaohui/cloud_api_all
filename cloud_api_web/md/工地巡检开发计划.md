## 1. 项目目标和已确认事实

目标是在现有平台上建设面向风电场施工区域的无人机巡检业务，支持固定机巢与车载移动机巢：划区、规划、任务执行、历史复飞、就近巡检、双光采集、站端分析、人员统计、隐患查看与报告。

现有前端为 Vue 3 + TypeScript + Vite，使用 Vue Router、Vuex、Element Plus 和 Ant Design Vue；相邻后端为 Spring Boot/Maven 项目。现有任务、设备、媒体和算法服务具备复用基础。评估来自方案正文、表格及本地相关源代码，未逐张核验插图，也未做现场飞行、算法效果或车站部署联调。

业务区别：现有风机巡检关注风机设备与叶片，光伏巡检关注组件与支架；本项目关注施工区域、人员及施工隐患。因此新增独立工地业务，不把光伏页面改名后作为最终交付。

### 1.1 用户已确认的部署要求（2026-10-20）

- 车载部署和固定部署均须脱网独立运行。
- 照片直接保存到各自部署端的本地存储，不以公网存储或另一端在线作为采集归档的前提。
- 设计按“外网不可达、现场设备与本地平台仍通过局域网通信”落实；不把脱网解释为无人机、机巢与平台之间完全没有通信。
- 确认的是运行方式和照片存储位置；算法部署位置、分析时效、是否回站汇总、是否跨端同步尚未确认。脱网独立并不自动产生必须开发双端同步的结论。

两种部署使用同一套软件与本地服务架构，差异集中在机巢是否移动、部署位置和现场资源配置。所需服务可运行在本机或本地局域网服务器，不预设必须全部放在一台电脑。

## 3. 规划假设与待确定事项

以下是假设，不是用户已经确认的最终需求。当前可以据此完成模块设计；相关结论确定前，不把对应能力标记为完成或承诺效果。

| 事项 | 当前规划方式 | 对实现的影响 |
|---|---|---|
| 分析时效 | 先按拍照后批处理设计，同时保留实时分析扩展点 | 实时视频分析需额外视频接入、推理和告警链路 |
| 自动抓拍 | 基础版为航点/间隔拍照，采集后识别 | 发现人员后自动变焦/跟踪/抓拍需要额外闭环 |
| 人数口径 | 分开保存单图人数与区域去重统计，算法未就绪时不生成虚假总人数 | 跨图关联及移动人员的统计需要样本和验收定义 |
| 分析位置与跨端交换 | 两端脱网独立、本地保存已确认；本地算法/回站分析/汇总同步待定 | 基础运行不依赖另一端；先预留结果和数据交换接口，不强制站端为主节点 |
| 处置深度 | 初版支持复核与处置记录 | 派单、整改、复查、销号作为可扩展子模块 |
| 就近距离 | 候选筛选暂按到区域边界的最短水平距离，机巢在区域内为0 | 范围默认2000米，可配置；最终规则需与验收一致 |
| 历史复飞 | 复用区域和采集参数，每次执行校核当前部署 | 不能在转场后直接沿用旧起飞点和相对高度 |
| 航线生成服务 | Java负责业务编排，通过独立适配接口调用规划能力 | 尚未检查外部C++服务通用覆盖能力，先核验再决定复用/新增 |

重点澄清“回站统一分析”与“实时人数/实时检测”的矛盾。两者保留在完整需求清单中，但不能用批处理演示代替实时能力验收。

## 4. 设计原则与业务架构

1. 新增工地领域模块，公共设备控制、飞行执行与媒体存储继续使用现有服务。
2. 前端负责交互和预览，区域有效性、最近区域选择、版本校验及执行条件由后端最终判断。
3. 计划和任务分离：同一计划可以多次执行，每次执行生成独立记录和不可变快照。
4. 工地元数据通过扩展表关联原平台 `plan_id`、`job_id`、`file_id`，避免把大量字段塞入光伏/风机实体。
5. 新增命名常量表示工地 `planType`。实施前搜索全部枚举、数据库和分支后分配数值，不预设“5一定空闲”。`task_type` 的立即/定时/条件含义保持独立。
6. 第一阶段以单次任务对应一个区域版本为基线；计划可产生多个区域任务。避免尚无媒体归属规则时把多个区域随意合并成一条任务。
7. 不依赖页面打开来触发工地分析；由后端持久化状态驱动，页面只查询和展示。
8. 车载端和固定端均本地启动、登录、划区、执行和归档；必要服务、资源与设备连接不依赖公网或另一端。算法是否随本地部署另行确定，不影响先完成本地采集。

```text
施工区域及版本 + 当前机巢部署 + 采集参数
                 ↓
             工地巡检计划
                 ↓
       航线预览/版本确认/KMZ文件
                 ↓
         现有平台任务创建与执行
                 ↓
      本地照片 + 工地执行记录 + 媒体清单
                 ↓
   分析位置待定：本地算法 / 后续汇总分析
                 ↓
       检测结果 + 人数统计 + 人工复核
                 ↓
              工地巡检报告
```

## 7. 数据模型草案

表名为建议，实际实施前核对现有命名、索引和迁移机制。所有业务表应包含工作空间、创建/更新时间，关键版本对象保持不可变。

| 建议表 | 主要字段/关系 | 阶段 |
|---|---|---|
| `construction_site` | 工地名称、编码、状态；可关联现有站点，不复用其风机专有字段 | 基础 |
| `construction_area` | site_id、name、enabled、current_version、施工状态 | 基础 |
| `construction_area_version` | area_id、version、GeoJSON边界、采集默认参数、修改原因 | 基础 |
| `construction_dock_profile` | dock_sn、fixed/mobile、vehicle_id/车辆标识、所属工地 | 基础/机动 |
| `construction_deployment` | dock_sn、部署版本、经纬高及高度基准、位置采样时间、来源、状态 | 基础/机动 |
| `construction_plan_ext` | 关联通用plan_id、area_version_id、采集参数、航线来源、分析配置 | 基础 |
| `construction_execution` | 独立execution_id、plan_id、job_id、区域/部署/参数快照、file_id、航线版本 | 基础 |
| `construction_media` | execution_id、原媒体file_id、镜头、拍摄时间、校验值、字节数、配对标识、就绪状态 | 采集/同步 |
| `construction_analysis_batch` | execution_id、输入清单版本、算法配置/模型版本、状态、重试数、错误信息 | 分析 |
| `construction_detection` | batch_id、media_id、类别、检测框、置信度、位置及定位来源 | 分析 |
| `construction_count_result` | batch_id、区域、时间窗、计数口径、估计值、算法值/人工修订值 | 分析 |
| `construction_issue`及事件表 | detection关联、类别、确认状态、处置记录、操作者/时间 | 结果 |
| `construction_report` | execution_id、batch_id、复核版本、模板版本、文件、生成状态 | 报告 |
| `construction_sync_batch`及明细 | 源/目标节点、对象ID、任务/媒体清单、校验、进度、状态、重试 | 双平台 |

关键约束：

- 区域版本唯一键 `(area_id, version)`；计划编辑采用版本号控制，旧版本保存冲突时明确返回。
- 任务下发按 `(workspace_id, idempotency_key)` 唯一；同键不同请求内容拒绝处理。
- 一个通用job只能绑定一个有效工地执行记录；同计划复飞必须产生新的execution/job，不能覆盖历史任务。
- 媒体以原平台文件ID/源节点全局ID去重，校验值用于完整性检查，不能仅按文件名归并。
- 分析批次绑定媒体清单和算法版本；重复回调不能重复生成检测结果或隐患。
- 删除已执行的区域/计划采用归档或禁止硬删，保留历史快照和报告关联。

迁移建议分为基础、分析、同步三个增量SQL文件；名称在实施时确定。先测试库验证，再部署目标库，不在本轮执行。

## 8. 接口草案

以下为拟新增接口，统一前缀 `/api/construction`，不是现有可调用接口。分页和返回结构跟随项目现有约定；坐标使用WGS84，经纬度为度，高度为米并携带基准类型。

| 方法和路径 | 用途 | 关键约束 |
|---|---|---|
| `GET /areas`、`GET /areas/{id}` | 区域列表及详情 | 工作空间过滤 |
| `POST /areas`、`PUT /areas/{id}` | 创建/更新区域 | 几何校验、预期版本号；更新产生新版本 |
| `GET /areas/{id}/versions` | 查询历史版本 | 供复飞追溯 |
| `POST /areas/{id}/archive` | 归档区域 | 不删除历史执行快照 |
| `GET /deployments/current?dock_sn=...`、`POST /deployments` | 查询/确认部署 | 保存定位时间及来源，校验部署变更 |
| `POST /routes/preview` | 导入航线适配或生成覆盖预览 | 返回preview_id、参数摘要、版本、到期时间、航点与估计值 |
| `GET /plans`、`POST /plans`、`PUT /plans/{id}` | 工地计划管理 | 关联通用计划及区域版本，保存不等于执行 |
| `POST /plans/{id}/execute` | 手动执行/复飞 | 提交preview_id及幂等键，服务端重新校核部署/版本 |
| `POST /dispatch/nearest/preview` | 最近区域候选和航线预览 | 默认2000米，明确无候选及不可执行原因 |
| `POST /dispatch/nearest/execute` | 按既定规则选区并执行 | 原子占用机巢；响应包含选定区域及execution_id；状态冲突不静默改派 |
| `GET /tasks`、`GET /tasks/{id}` | 工地执行记录及进度 | 返回关联job_id以复用现有控制台 |
| `GET /tasks/{id}/media`、`GET /tasks/{id}/results` | 媒体和结果 | 区分未上传、未分析、无异常和分析失败 |
| `POST /tasks/{id}/analysis` | 请求分析/重分析 | 幂等创建批次，返回batch_id及状态，不长时间阻塞HTTP |
| `POST /analysis/callback` | 外部算法结果回调 | 调用方认证、批次关联、重复回调保护 |
| `GET /issues`、`POST /issues/{id}/review` | 隐患检索及复核 | 保存原算法结论与复核轨迹 |
| `POST /issues/{id}/dispositions` | 记录处置 | 完整派单流程另行扩展 |
| `POST /tasks/{id}/reports`、`GET /reports/{id}` | 创建/查询报告 | 文件生成完成后才标记READY，失败可重试 |
| `GET /reports/{id}/download` | 下载报告 | 校验归属及文件状态 |
| `GET /sync/batches`、`POST /sync/batches`、`POST /sync/batches/{id}/retry` | 双平台同步控制 | 文件传输/分片协议在部署方案确定后细化 |

规划请求建议包含：`area_version_id`、`dock_sn`、`deployment_version`、`route_source`（generated/imported）、`source_file_id`、`flight_params`、`capture_params`、`analysis_profile_id`。航高明确标记 `height_reference`，禁止把相对航高直接当作绝对高。

客户端预览只用于展示。执行时重新检查当前部署、参数和区域版本；若变化影响航线，要求生成新预览，不能执行陈旧预览。预览可显示轨迹不等于已经通过地形或障碍物校验。

## 9. 核心业务实现计划

### 9.1 工地覆盖规划

1. 解析区域多边形，校验经纬度范围、重复点、自相交及有效面积；初版若不支持孔洞/多块区域则明确拒绝，不偷偷截断几何。
2. 使用适合当地范围的米制坐标计算覆盖航段，避免直接把经纬度差当作米。
3. 根据现场样本确定的取像参数配置条带方向、间距和拍照间隔；输出进场、巡检、返场段。
4. 对凹多边形的分段连接、区域外绕行、限制区域、地形及障碍物约束单独校验；没有所需数据时返回未校验状态，不能宣称自动避障。
5. 接入现有KMZ生成能力，统一输出机型、镜头、拍摄动作、高度模式和返航参数。先核对`dfe-wayline`实际入口及外部规划服务能力。
6. 不把云渲染服务的`/api/wayline/build-kmz`代理设为工地基础功能唯一出口；工地后端应通过规划适配器接入实际生成服务。

导入航线可作为第一阶段闭环入口，但最终必须交付方案要求的自动划区规划。不得靠修改导入航线起飞点就声称完成任意转场适配。

### 9.2 下发与转场

执行前校核部署版本、定位时效、设备状态、区域启用、航线有效性和工作空间。机巢占用检查与创建下发请求需要并发保护，不能只在前端禁用按钮。

建议下发记录状态为 `PREPARED → SUBMITTING → ACCEPTED / FAILED / UNKNOWN`。设备或外部服务超时可能已经接收任务，记录为UNKNOWN并按任务关联查询确认，不能直接重发导致重复起飞。任务实际执行进度继续采用原平台状态。

转场后生成新部署版本，旧预览失效；历史执行保留旧部署快照。定时任务在实际触发时也必须做同样检查。

### 9.3 媒体完整性与同步

飞行完成、本地媒体收齐、分析完成分别建状态；若后续启用同步，再增加接收端收齐状态，不合成一个“完成”标记。保留中断任务的已有图片；图片缺失/媒体预期数量未知时明确标识，不能简单因短时间无新增文件就宣称齐全。

双光配对优先使用设备文件关联信息；缺失时按任务、航点及时间匹配并记录不确定性，不默认两条镜头文件一定一一齐全。

已确认的基础架构：车载端和固定端各自维护本地区域、计划、任务和媒体，均可独立新建与运行，不强制从固定端拉取主数据。每个机巢明确当前控制节点，避免两端同时下发。

跨端交换为待确定需求。若确认需要，再实现全局ID、版本冲突处理、清单校验、可重试同步和结果回传；同步失败不阻塞本地采集归档。不能因确认脱网运行就认定必须交付自动车站同步。

### 9.3.1 本地运行与存储实施项（必需）

1. **本地运行栈**：前端静态站点、Java服务、数据库、项目实际使用的Redis/MQTT服务、媒体接收/存储及直播媒体服务部署在本机或现场局域网；自动规划所需服务同样本地可达。按实际依赖盘点交付，不盲目新增组件。
2. **存储链路**：核对机巢媒体上传凭证、对象存储/文件服务配置、回调和下载地址，均指向机巢和浏览器可达的本地服务。浏览器手动下载不能替代服务端接收照片。
3. **原图落盘**：原始可见光、红外文件持久化存储，保留测温所需原文件；数据库记录相对路径或对象键及任务/区域/镜头关联，根目录可配置。照片不能仅保存在浏览器缓存、临时目录或无人机存储卡。
4. **地图和资源**：离线提供工作区域所需的瓦片、影像、脚本、字体、图标及选用的模型/地形。已见`index.html`加载本地`/amap/AMap3.js`、地图Hook创建瓦片图层，但这不证明所有资源均无外网依赖；继续检查脚本内部加载及地图请求。现有Vite本地瓦片插件仅开发期有效，正式部署须配置本地资源服务。
5. **运维与恢复**：配置本地服务启动、断电重启恢复、存储容量提示、上传中断重试、完整性检查及备份/导出；具体目录、容量和保留期按现场设备确定。磁盘满或写入失败时不标记归档成功，不默认清理原图。
6. **外部依赖审计**：逐项检查运行配置、登录鉴权、地图、视频、航线生成、设备时间/定位和RTK等链路是否依赖外部服务；硬件侧脱网要求必须通过目标设备验证，不能仅修改平台URL就认定脱网执行可用。
7. **验收环境**：保持现场局域网、断开互联网和另一部署端，清除浏览器资源缓存后冷启动，验证登录、地图划区、航线、设备连接、任务、直播及原图归档；停止并重启本地服务后仍能查询历史任务和照片。两种部署分别验收。

### 9.4 分析与统计

分析状态建议为 `WAITING_MEDIA / WAITING_SYNC / QUEUED / RUNNING / PARTIAL / SUCCEEDED / FAILED`。由持久化批次和后台执行器驱动，重启后能恢复待处理任务。

算法适配器约定类别、检测框坐标基准、置信度、模型版本、错误结构和输入类型。至少覆盖方案列出的人员、安全帽、抽烟、安全绳、烟雾、火焰、温度异常，但支持声明须来自实际模型验证。

人员单图数量与跨图去重人数分开存储；跨图统计绑定区域、采集时间窗和算法版本。未实现去重时只显示已有单图统计，整体需求仍为未完成。抽烟、安全绳及高温必须用真实航高/焦距/热成像输入做效果评估。

异常定位保留定位来源及误差说明；拍摄设备的GPS不能直接作为地面隐患坐标。模型未返回可信地面位置时，先展示所属施工区域和证据图片。

### 9.5 结果与报告

结果页保留原图、分析图、检测框、类别、置信度、模型版本和人工修订。初版隐患支持待确认、已确认、误报，以及独立处置记录；完整整改流程待范围确认。

工地报告包含区域和部署信息、执行时间、航线版本、媒体完整性、人数口径、隐患明细、复核结果及分析未完成项。无异常也能生成报告，不能只从缺陷列表拼出整个任务结论。

报告绑定分析和复核版本；生成新版本不覆盖旧文件。生成失败保留错误状态并可重试，成功落盘后再更新READY。

## 11. 测试与验收计划

### 11.1 新功能的关键行为测试

- 几何与规划：矩形、凹多边形、无效/自交区域；覆盖间距；无地形数据时的状态；航高转换；导入航线动作保留。
- 就近调度：机巢位于区域内、恰好范围边界、无候选、区域禁用、位置过期、部署变更、距离并列。
- 执行幂等：重复点击、并发请求、同幂等键不同载荷、下发超时但已接受、定时触发时位置变化。
- 版本与归属：区域更新不改旧任务；同计划复飞新建执行；跨工作空间访问被拒绝。
- 媒体/同步：乱序文件、缺红外、重复文件名、断网恢复、重复回调、服务重启、部分文件损坏。
- 算法：媒体未齐不误标成功；失败可重试；重复结果不重复入库；跨图人数不以简单累加冒充。
- 报告：无异常、部分分析、生成失败重试、复核后生成新版本。

### 11.2 工程验证

- 前端：先对新增模块做类型/SFC与定向ESLint检查，再运行适用构建；不把旧仓库已有类型错误直接算作新模块失败。
- `npm run lint`带`--fix`，Vite的ESLint插件也配置了自动修复；验证前后检查差异，避免把无关改动带入交付。
- `npm run build`的prebuild会刷新模型清单；实施时记录并检查副作用。文档阶段不运行这些命令。
- 新增纯逻辑测试可沿用现有Node脚本模式，例如`test-construction-geometry.cjs`；不为简单展示组件编写只镜像实现的测试。
- 后端：在实际Maven依赖就绪后，针对区域、调度、分析幂等及同步服务执行JUnit/Mockito测试；检查是否有`skipTests`配置并确保目标测试真正执行。
- 原风机、光伏、普通航线的创建、下发、分析和报告至少做针对性回归。

## 12. 部署、迁移与回退计划

1. 新模块使用功能开关，默认关闭；增量表先部署到测试环境。
2. 车载和固定端分别配置本地数据库、存储、设备通信、地图、媒体和规划服务，准备无需现场联网下载的部署包；算法部署位置待定。

4. 部署前备份相关业务数据，记录迁移版本及新增枚举值。
5. 回退优先关闭入口/停止新工地任务接收；已受理飞行任务仍保留状态观察与现有控制能力。
6. 不自动删除新表、已采集媒体和报告；数据回退另行制定，避免破坏历史记录。
