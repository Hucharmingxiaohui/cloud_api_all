# 工地巡检算法接口协议 V1.0

> 日期：2026-10-27  
> 用途：供平台与算法服务双方开发、联调使用。按本次讨论编制，属于接口约定，不表示现有代码已完成接入。  
> 传输方式：站内局域网 HTTP + JSON；原图及分析结果图均采用 Base64。  
> 精简原则：不传校验码、文件大小、原始文件名、模型版本等字段；不重复传平台已有的航点、计划信息。

## 1. 业务流程及双方职责

**飞行任务是提交分析的单位，巡检区域（工作面）是人数去重汇总的单位，照片是具体检测的单位。**

1. 一次飞行可以巡检一个或多个区域，采集的照片均保存到平台所在部署端的本地存储。
2. 回站连接分析主机后，人员在该飞行任务结果中手动提交分析。连接主机、查询状态不会自动提交分析。
3. 平台按执行时的区域、航点及配置快照，为每张照片确定所属区域和最终检测项目。
4. 平台一次提交本次分析所需的完整照片集合。分析服务保存请求并返回分析任务ID，在后台异步执行。
5. 分析服务完成逐图检测，对同一区域内所有要求人数统计的照片进行跨图去重，形成区域人数结果。
6. 平台轮询状态，读取区域人数，逐张取回检测结果和标注结果图，解码后保存本地，用于结果展示、人工复核和报告。

| 平台侧负责 | 算法侧负责 |
|---|---|
| 原图采集、保存、照片与区域/航点关联 | 接收图片，按照片要求调度模型 |
| 多级检测配置及执行快照 | 单图隐患检测、单图人数统计 |
| 人工提交、传输、网络重试、状态查询 | 同一区域的多角度照片人数去重 |
| 保存结构化结果和结果图，按区域展示、生成报告 | 返回每项检测状态、区域人数及综合标注图 |

分析任务是飞行任务下的一次分析批次，不是新的飞行任务。同一飞行任务重新分析时使用新批次，保留原批次结果。

## 2. 检测项目配置规则

> 2026-10-29平台实现说明：已实现可编辑的工作空间默认规则、工作面覆盖及航点覆盖，默认初始值仍为全部12类。平台另行保存红外开关、温度阈值及最小热点像素数，默认关闭红外；该保存结构不是本协议的算法报文，本轮没有接入新的分析提交、结果整理或报告生成。后续红外算法传输字段需双方确认。操作及快照生效时机见[工地巡检检测配置说明.md](工地巡检检测配置说明.md)。

优先级：**航点独立配置 > 区域统一配置 > 默认全部12类**。

- 默认所有航点请求全部12类检测。
- 区域可统一选择需要的检测项目。
- 航点未单独配置时继承区域配置；单独配置后使用该航点完整的勾选列表，不再与区域配置叠加。
- 航点支持恢复继承区域配置。后续修改区域配置只影响仍继承区域配置的航点。
- 保存区分“未单独配置”和“单独配置为空”；空列表表示该航点不参与分析，其照片不提交给分析服务。整个任务没有待分析照片时，平台不创建分析批次。
- 检测配置与区域、航点关系随执行任务冻结；历史任务分析使用对应快照，不能直接读取后来修改的航点配置。主动调整后重新分析须生成新批次并保存本次配置。
- 平台将继承关系计算为每张照片的 `checks`，算法侧只执行最终列表，不处理区域/航点继承。
- “全部检测”在请求中展开为全部12个编码，不使用含义可能变化的 `all` 通配符。
- 未匹配到区域的照片使用 `area_id: null`；可按任务默认配置请求单图检测，但不能自动归入其他区域的人数结果。
- 默认全选表示请求检测，不表示12类模型都已就绪。尚不可用、镜头不适用或照片无法判断必须明确返回状态。

## 3. 检测类别编码

| 编码 | 名称 | 主要结果 |
|---|---|---|
| `missing_helmet` | 未佩戴安全帽 | 异常框 |
| `phone_use` | 违规玩手机 | 异常框 |
| `smoking` | 工作场所吸烟 | 异常框 |
| `person_fallen` | 人员倒地 | 异常框 |
| `missing_safety_clothing` | 作业中未穿着安全服 | 异常框 |
| `person_count` | 人员数量统计 | 单图人数、区域去重人数，可附人员框 |
| `fire_smoke` | 火灾烟雾 | 异常框，可区分火焰/烟雾 |
| `adverse_weather` | 恶劣天气 | 图像级异常判断 |
| `animal_intrusion` | 动物入侵 | 异常框 |
| `barrier_crossing` | 人员违规跨栏 | 异常框 |
| `person_under_lifting_load` | 塔吊吊物下方站人 | 异常框 |
| `missing_hook_latch` | 防脱钩缺失 | 异常框 |

类别编码保持稳定。恶劣天气的具体子类、塔吊吊物下方范围、安全服标准等识别判据由现场与算法方进一步确认；不能仅以接口打通认定模型达到验收要求。

## 4. 人数统计与区域去重规则

1. 仅 `checks` 包含 `person_count` 的照片参与人数统计和区域去重；其他照片只执行自己的检测项目。
2. 每张参与人数统计的照片，必须返回单图人数或明确的未成功状态。
3. 按“本次分析任务 + area_id”组织去重，不混合不同区域或历史任务。照片之间的重复人员由算法侧处理，平台不再次计算。
4. 同一区域所有参与统计的照片收齐并处理后，再返回最终区域去重人数。可见光、红外若都请求人数统计，也属于该区域同一组去重输入；算法不支持的镜头必须明确返回不适用状态。
5. 区域人数不能用单图人数直接求和或取最大值冒充去重结果。区域级成功必须表示已完成约定的去重处理；只有一张成功统计照片时，区域人数可等于该单图人数。
6. 如部分统计照片失败、模型不适用或无法判断，区域结果不得将其悄悄排除并标记成功；区域 `count` 返回 `null`，状态及说明指出统计不完整。成功的单图结果仍保留。
7. 区域没有任何请求人数统计的照片时，返回 `not_requested` 和 `count: null`。
8. `area_id: null` 的照片可以返回单图人数，不生成虚构区域，也不并入某个工作面。
9. 区域人数口径为本次采集照片集合识别到的去重人数，不宣称为严格同一时刻的实时在场人数。
10. 不同区域之间可能仍有重复人员；平台不得将区域人数简单相加并称为全工地去重总人数。本版不要求跨区域去重。

## 5. 通用报文约定

- 请求和响应均使用 `Content-Type: application/json`，文本编码UTF-8。
- 原图 `data` 和结果图 `image` 使用标准Base64，不含 `data:image/...;base64,` 前缀，不换行。
- 原图直接对文件字节编码，不先缩放或转码；尤其保留红外原始文件信息。算法需要读取哪些红外信息，另行与机型样本核对。
- 分析结果图统一为JPEG；平台Base64解码后保存为 `.jpg`，原图和结果图分别保存。
- 区域ID、照片ID均作为不透明字符串处理；算法不得按名称或ID文本猜测区域、航点。
- 一个请求内照片ID不得重复；同一照片只填写一个区域归属。`checks` 使用第3节编码，不允许未知编码或重复编码。
- 不传校验码。分析服务仍须检查JSON、Base64和图片是否可解码；失败返回错误，不能当作正常图片。
- 非2xx响应统一为 `{ "message": "错误原因" }`。建议400表示参数错误，404表示任务/图片不存在，409表示状态冲突，413表示请求过大，503表示服务暂不可用。
- 网络访问地址、访问令牌/鉴权方式、请求体大小和超时上限由部署双方统一配置，不放入每张照片的业务字段。

## 6. 接口清单

以下路径相对于分析服务基础地址，例如 `http://站内分析主机:端口`。基础地址由平台配置。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/health` | 检查分析服务连接 |
| POST | `/analysis/tasks` | 提交整次分析所需照片，创建异步分析任务 |
| GET | `/analysis/tasks/{task_id}` | 查询进度，完成后同时返回各区域去重人数 |
| GET | `/analysis/tasks/{task_id}/images/{image_id}` | 获取单张照片的检测结果及Base64标注图 |

除连接检查外，核心业务接口为提交、查询、取图三个。

### 6.1 检查连接

```http
GET /health
```

成功返回HTTP 200：

```json
{
  "status": "ok"
}
```

该接口只表示服务可访问，不代表12类模型全部可用；实际模型可用情况在对应检测项结果中返回。

### 6.2 提交分析任务

```http
POST /analysis/tasks
```

请求示例：一次飞行包含A、B两个工作面，A有两个角度，B有一张照片。

```json
{
  "request_id": "batch-001",
  "images": [
    {
      "id": "photo-001",
      "area_id": "area-A",
      "type": "visible",
      "checks": ["person_count", "missing_helmet"],
      "data": "照片1的Base64"
    },
    {
      "id": "photo-002",
      "area_id": "area-A",
      "type": "visible",
      "checks": ["person_count"],
      "data": "照片2的Base64"
    },
    {
      "id": "photo-003",
      "area_id": "area-B",
      "type": "visible",
      "checks": ["person_count", "fire_smoke"],
      "data": "照片3的Base64"
    }
  ]
}
```

示例中的Base64文字为占位说明，联调必须使用实际编码。

| 字段 | 必填 | 说明 |
|---|---|---|
| `request_id` | 是 | 平台生成的本次分析唯一标识，建议UUID；平台本地关联原飞行任务 |
| `images` | 是 | 非空照片数组，包含本批次完整待分析照片集合 |
| `images[].id` | 是 | 平台照片ID，唯一匹配原图与结果 |
| `images[].area_id` | 是，可为null | 巡检区域/工作面ID；去重分组依据 |
| `images[].type` | 是 | `visible` 可见光、`infrared` 红外、`unknown` 未确认 |
| `images[].checks` | 是 | 该照片最终检测编码列表，不为空 |
| `images[].data` | 是 | 原图Base64 |

成功接收并持久化后返回HTTP 202：

```json
{
  "task_id": "analysis-001"
}
```

处理约定：

- 接收完整请求并可靠保存照片与任务后再返回任务ID，检测异步执行，不等待全部模型完成才响应。
- 相同 `request_id`、相同请求内容重试，返回同一 `task_id`，不得重复执行；相同标识但内容不同返回409。
- 接收失败不能留下会被当作完整任务执行的半份照片集合。模型不可用不等于请求格式错误，正常接收后在相应检测结果标明。
- 飞行任务ID、航点ID及区域名称不必重复传输，平台通过本地批次关系和照片ID即可关联；`area_id` 因为涉及算法分组必须传输。
- 本版一次请求就是完整集合，请求结束即确认照片收齐，不再设置“开始分析”接口。用户没有选入本次分析的照片不属于该集合。
- 大任务不能随意拆成彼此独立的分析任务后再相加人数。同一工作面的统计照片必须处在同一去重上下文。超出约定请求上限时返回413，平台提示；如实际照片量无法一次提交，双方另行扩展“同一任务分次追加照片＋确认收齐”，不能由任一方擅自改变本版含义。

### 6.3 查询进度与区域人数

```http
GET /analysis/tasks/analysis-001
```

执行中响应：

```json
{
  "status": "running",
  "finished": 2,
  "total": 3
}
```

完成后响应：

```json
{
  "status": "completed",
  "finished": 3,
  "total": 3,
  "areas": [
    {
      "area_id": "area-A",
      "status": "success",
      "count": 10
    },
    {
      "area_id": "area-B",
      "status": "success",
      "count": 5
    }
  ]
}
```

区域去重未成功示例：

```json
{
  "area_id": "area-A",
  "status": "unavailable",
  "count": null,
  "message": "单图人数已返回，跨图去重模型尚未就绪"
}
```

| 字段 | 说明 |
|---|---|
| `status` | 批次状态：`queued`、`running`、`completed`、`failed` |
| `finished` | 已结束逐图处理的照片数，包含明确结束为失败/不适用的照片；不是成功检测数 |
| `total` | 创建请求中的照片总数 |
| `areas` | 在 `completed` 时必返；包含输入中每个非null区域，各区域恰好一项；无有效区域时为空数组 |
| `areas[].count` | 区域去重人数，非负整数；未成功统计时为null |
| `message` | 失败或无法完成的原因，成功时省略 |

状态约定：

- `queued`：等待执行；`running`：逐图检测、区域去重或结果图生成尚未完成。
- 即使 `finished == total`，只要区域去重或结果保存尚未结束，仍保持 `running`。平台不能仅凭照片进度判断整批完成。
- `completed`：全部请求项目已得到终态、区域汇总已得到终态，结果已保存；不表示每个项目都成功，更不表示现场无异常。
- `failed`：无法正常完成整个分析任务，附 `message`。部分模型失败时，优先保留其他结果并以 `completed` 返回，由逐项状态说明。
- 区域状态使用第7节状态，另允许 `not_requested` 表示该区域没有照片请求人数统计。
- 平台建议每3～5秒轮询一次，结束后停止轮询。网络中断后继续查询原任务，不新建分析任务。

### 6.4 获取单张照片结果和结果图

```http
GET /analysis/tasks/analysis-001/images/photo-001
```

响应示例：

```json
{
  "checks": [
    {
      "code": "person_count",
      "status": "success",
      "count": 8
    },
    {
      "code": "missing_helmet",
      "status": "success",
      "boxes": [
        {
          "rect": [1200, 650, 180, 240],
          "score": 0.93
        }
      ]
    }
  ],
  "image": "综合标注JPEG图Base64"
}
```

该照片对应请求中的 `photo-001`，路径已包含照片ID，响应不再重复传ID和区域。

- `checks` 必须与提交时的检测列表逐项对应，顺序可不同，每项恰好一次。不能省略不可用、失败或不适用项目。
- `person_count.count` 为该张照片的人数，非负整数；只有成功统计且无人时返回0，未成功时为null。
- 普通隐患检测成功但没有异常时返回 `boxes: []`。
- `boxes[].rect` 为 `[左上角x, 左上角y, 宽, 高]`，单位像素。坐标依据按EXIF方向纠正后的原尺寸图像；算法内部缩放后须换算回来，结果图也使用该方向与尺寸。
- `boxes[].score` 为置信度，取值0～1；`boxes[].label` 可选，用于火焰、烟雾等子类。人员统计可额外返回人员框，不强制要求。
- 图像级异常（如恶劣天气）可使用 `label`、`score` 表达异常子类和置信度，不要求虚构矩形框；未检出图像级异常时 `label: null`，省略 `score`。具体子类在算法验收说明中统一。
- `image` 为该原图的一张综合标注JPEG图，包含本次成功项目的异常标记、类别文字及单图人数（若请求并成功统计）。不要把区域去重人数错误标为该照片人数。
- 原图无异常时也可返回同尺寸结果图，标明已完成项目；部分项目未完成时不得笼统标为“全部正常”。
- 结果图生成失败时 `image: null`，增加 `image_error` 说明原因；已完成的结构化检测结果仍须返回。
- 平台在批次 `completed` 后逐张取结果，避免把所有结果图放在一次响应中。尚未生成稳定结果时返回409；任务或照片不存在返回404。任务结束后的重复获取应返回同一版本结果。

## 7. 检测项及区域人数状态

| 状态 | 含义 | 示例 |
|---|---|---|
| `success` | 已成功完成指定检测或区域去重 | 检测无异常、单图0人、区域去重10人均可为成功 |
| `unavailable` | 所需模型或能力尚未提供 | 防脱钩模型训练中、跨角度去重能力未接入 |
| `not_applicable` | 输入不适用该能力 | 可见光模型不支持输入红外照片 |
| `unassessable` | 图片质量/可见内容不足，无法判断 | 目标过小、严重模糊、遮挡 |
| `failed` | 执行或汇总异常 | 推理失败、图片解码异常、部分统计输入失败导致无法形成完整区域人数 |
| `not_requested` | 仅区域人数允许：区域未请求人数统计 | 该区域所有照片只检测隐患 |

非成功状态应返回 `message`。任何未成功的人数都为null，不能填0；不得把模型未训练好、照片看不清当作“未发现异常”。

例如：

```json
{
  "code": "person_count",
  "status": "unassessable",
  "count": null,
  "message": "人员遮挡严重，无法可靠统计"
}
```

## 8. 保存、重试和报告使用

- `request_id` 由平台生成并保存，建立与原飞行任务、执行快照的关系；网络重试使用原标识，用户主动重新分析才生成新标识。
- 分析服务应持久化任务、去重结果和结果图；服务重启后仍可按原 `task_id` 查询。无法恢复执行时明确标记失败，不永久停在运行中。
- 平台保存结果时按“分析批次＋照片ID”更新，按“分析批次＋区域ID”保存区域人数，重复拉取不增加重复记录。
- 原图与分析结果图分开保存，报告引用指定分析批次的本地结果图和区域人数，不依赖分析主机长期在线。
- 分析服务不在首次获取后立即删除结果；保留期限与清理方式由双方部署时约定，不能早于平台取回所需时间。
- 本版不传算法版本；平台通过独立分析批次保留各次结果，不覆盖历史报告。

## 9. 联调验收案例

1. **单区域多角度**：A区域两张统计照片分别8人、6人，测试样本确认有4人重复；返回单图8、6及区域去重10，不返回14或默认取8。
2. **多区域一次飞行**：同一批次同时提交A、B区域，分别返回各区域去重人数，不混合区域照片。
3. **检测配置差异**：同区域一张请求人数统计、一张只请求安全帽；仅第一张参与人数去重，第二张不能额外返回未请求的人数结果。
4. **无人数需求**：区域所有照片未选择人数统计，区域返回 `not_requested`、`count: null`。
5. **模型逐步上线**：未就绪检测项返回 `unavailable`，其他项目正常执行；单图模型可用但去重模型未就绪时，保留单图人数，区域返回不可用，不冒充去重。
6. **空值与零值**：确认无人返回0；图像模糊、模型不适用或失败返回null及对应状态。
7. **统计输入不完整**：同区域一张统计照片失败，其他单图结果仍返回，区域不得标记完整去重成功。
8. **未知区域**：照片 `area_id` 为null时可做单图检测，不计入其他区域去重。
9. **重复提交与断线**：相同请求标识重试返回同一任务；轮询或取图中断后恢复，平台和分析侧均不重复建任务或结果。
10. **图片往返**：Base64原图能正确解码；结果图JPEG可显示并写入报告，框坐标与方向一致；结果图失败不丢失已完成的结构化检测。
11. **整体完成时机**：逐图处理完成但区域去重未结束时保持 `running`，区域结果和结果图就绪或明确失败后才返回 `completed`。
12. **异常请求**：未知类别、重复照片ID、无效Base64、请求过大均给出明确错误，不产生部分执行却被当作完整的批次。

## 10. 开发边界及待双方确认事项

- 本文是本轮确定的接口目标。平台现有本地归档、手动分析基础入口可复用，但区域/航点检测配置、该报文适配、区域人数及报告接入仍需开发，不能视为已实现。
- 算法方需明确每类现有/待训练能力，以及多角度人数去重所需的采集条件。若仅凭输入照片无法满足要求，应在开发前提出最小必要辅助信息，不能静默以简单求和替代。
- 请求体大小上限、单次最大照片量、超时、并发、访问鉴权及结果保留期，双方在部署联调前确认。本版坚持整次分析完整集合；实际容量不足时再共同扩展分次传输，不把同一工作面的去重输入拆散。
- 真实可见光/红外图片格式与元数据、图像级天气子类、机械风险的判定范围，需结合实际机型和现场样本确认。
