# 龙源风电场工地巡检：现有平台复用与开发差距

评估日期：2026-10-19。

需求更新（2026-10-20）：用户已确认车载和固定部署均脱网独立运行，照片直接保存至各自本地。后续以[工地巡检开发计划.md](工地巡检开发计划.md)为主；分析位置及跨端同步需求仍待确定。

依据：`D:\uav\龙源工地巡检\无人机风电场工地巡检方案-东方电子20260914.docx` 的正文、表格，以及本地 `cloud_api_web` 与相邻 `cloud_api_serve_git/sample` 的相关代码。未逐张核对方案插图，未进行设备、算法服务、飞行或部署联调。下文“已有”指代码基础存在，不等同于该项目验收通过；“未发现”限于本次检索范围。

## 1. 结论

建议在现有平台增加独立的“工地巡检”业务模块，复用设备接入、航线文件、任务执行、直播控制、媒体管理和报告基础设施。

项目的主要增量是：施工区域及计划管理、通用区域覆盖航线、移动机巢转场与就近调度、车端与站端数据同步、施工安全算法接入、跨图人数统计、工地结果与报告。

现有风机巡检主要面向风机设备/叶片，光伏巡检面向组件及支架；两者都不等于施工现场人员与安全巡检。不能仅替换页面名称或算法类别完成迁移。

## 4. 建议新增模块与数据关系

建议增加“工地巡检”业务入口，包含：施工区域、巡检计划、任务结果、隐患记录、统计报告。车载部署状态可以整合到现有设备/控制台。

建议数据关系：

```text
项目/工地 → 施工区域 → 区域版本与巡检参数
机巢 → 固定/移动属性 → 部署记录（位置、时间、定位有效性）
区域版本 + 部署记录 → 巡检计划 → 执行任务
执行任务 → 媒体清单 → 同步批次 → 分析批次
分析批次 → 单图检测结果/人数统计/隐患记录 → 人工复核 → 报告版本
```

为新业务分配独立计划类型，梳理计划创建、任务完成、算法启动、结果查询、报告生成的类型分支，避免被现有“风机/光伏才分析”的逻辑跳过。

## 5. 几项必须单独设计的能力

### 5.1 工地区域覆盖航线

区域需要支持施工状态、启停、边界版本、负责人，以及高度、速度、航向、拍照间隔/重叠、云台角度、双光模式。规划结果要包含进场段、巡检段、返场段及预计里程/耗时。

人员识别与普通测绘的取像目标不同。先由样本测试确定可以识别人和细小行为的拍摄参数，再约束规划；仅做弓字航线不能证明抽烟或安全绳识别可用。

高度需明确相对起飞点、相对地面或绝对椭球高，并在模型、规划与KMZ之间一致转换。施工障碍物与区域边界需要可更新；现有三维编辑可以辅助检查，但不代表自动避障规划已完成。

### 5.2 移动机巢与就近巡检

方案的“2公里”作为业务候选范围，不直接等同于可安全执行。建议流程：读取当前有效部署位置 → 筛选启用施工区域 → 应用距离与待巡规则 → 检查任务/设备可用性及航程 → 选定区域 → 生成或重算连接航段 → 下发。

需约定距离计算使用区域边界、入口还是中心点；保存位置数据时间，拒绝用陈旧位置触发自动规划。明确没有候选、候选已巡、设备忙、定位失效、航线生成失败时的结果。平台可以记录部署准备检查，但不能仅从地图位置推断车载设备已具备起飞条件。

历史复飞应复用施工区域和拍摄目标；转场后不能无条件复用旧起飞参考点、返航路径和相对高度。

### 5.3 车端与站端数据链路

2026-10-20用户确认：车载与固定部署均须脱网独立运行，照片直接保存在各自本地。两端均具备本地服务和持久存储，运行不依赖公网或另一端。设备与平台仍通过现场局域网通信。

本地运行需要核验数据库、MQTT/媒体服务、地图资源、航线生成和设备侧外部依赖，原图应通过媒体接收链路保存到本地磁盘或本地对象存储，不能仅靠浏览器下载。

分析在本地还是后续汇总处理、是否需要自动跨端同步仍待确定。如确需数据交换，再补全局ID、媒体清单与校验、重试、去重及结果回传；不将跨端同步作为两端独立工作的前提。

### 5.4 算法与人数统计

现有算法HTTP入口只证明具有接入基础；没有证据证明当前算法服务已经支持施工类别。

建议统一结果字段：任务、区域、图片、类别、检测框、置信度、拍摄时间、模型版本；可定位的结果增加位置与定位来源。图片GPS通常标识拍摄位置，不能直接当作隐患地面位置。

单图检测人数不能直接相加得到工地总人数。多角度照片中同一人重复出现且会移动，需要确定计数时间窗、重叠区域处理、跨图关联、遮挡处理及人工校正。无法保证去重时应明确展示统计口径，不宣称精确唯一人数。

抽烟、安全绳等类别需要先用目标现场、目标航高和焦距的真实样本验证。热成像显示和实时测温基础也不能替代自动温度异常/火灾判定；需验证原始测温数据、规则及结果关联。

## 6. 方案中的待澄清口径

- “全部任务结束后回站分析”与“人数实时、实时检测”并存。基线建议按离线批处理闭环设计，实时视频AI单独作为增量需求；最终以项目确认口径为准。
- “自动抓拍施工人员”可能指固定航点拍照后识别人，也可能指发现人员后触发相机/变焦/跟踪。后者需要实时感知到飞行/负载控制的额外链路。
- “人数”是单图人数、一次区域巡视人数、某时刻在场人数还是全天唯一人数，验收方法不同。
- “处置”是查看并记录结论，还是派单、整改、复查、销号，需单独确定。
- 两端脱网独立与本地存图已确认；待细化本地设备资源、地图范围、分析位置与跨端交换范围。
- 方案文字称支持条件触发计划；本次看到通用页面提供立即/定时执行，其他触发类型需继续核验，不能按方案描述直接认定已交付。
- 设备规格及车载部署要求未在本次代码评估中核验，不将方案表格作为当前官方能力证明。

## 7. 建议实施顺序与验收

1. **先做样本与部署验证**：确认车端/站端拓扑，验证一条导入航线的双光采集与回传，取得工地样本，评估算法及人数统计口径。
2. **建立基础业务闭环**：施工区域 → 导入/人工航线或初版自动规划 → 工地计划 → 下发执行 → 媒体归档 → 结果与基础报告。复用现有飞行执行能力，新增工地业务类型。
3. **完善机动巡检**：动态部署位置、2公里候选选择、转场后复飞、自动覆盖规划、失败处理。本地运行和存储已是基础阶段要求，跨端同步按后续确认范围安排。
4. **完成智能分析交付**：施工类别模型接入、异步分析队列、复核、人数统计和正式工地报告。算法样本工作与前几阶段并行推进。
5. **按确认范围扩展**：实时视频AI、目标触发抓拍、完整整改闭环、三维场景增强和现场喊话。

验收至少覆盖：区域版本可追溯；机巢转场后正确选区和规划；完整保留双光媒体；中断后同步可恢复且不重复分析；历史复飞关联正确区域；算法在约定样本上验证；人数按约定时间窗和去重口径评估；报告既展示异常，也能表达无异常及未完成分析。

本次未给出复用百分比或开发工期：代码复用率不能代表交付工作量，算法成熟度、双端部署模式、车载设备联调和统计口径尚未确定。
